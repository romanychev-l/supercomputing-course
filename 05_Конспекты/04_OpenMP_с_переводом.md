## Слайд 3. Общая память

🗣 **ГОВОРИМ:**

> «OpenMP в нашем первом приближении — несколько потоков 1 процесса, работающих с общей памятью. На рисунке 2 процессора, в каждом по 2 ядра, а оперативная память общая. Поток может прочитать тот же массив, что и его сосед, без явной пересылки сообщения. Но общая память не означает одинаковое время доступа и не означает безопасность одновременной записи. Если 2 потока меняют 1 счётчик, их действия нужно согласовать. Аппаратные кэши эту обязанность программиста не отменяют».

## Слайд 5. Обмен через общие объекты

🗣 **ГОВОРИМ:**

> «Преимущество общей памяти — данные уже доступны всем потокам по общим адресам. Если массив только читается, его обычно не нужно копировать каждому участнику. Если каждый поток записывает свой элемент результата, обмен тоже получается простым. Но общий изменяемый объект создаёт конкуренцию. Наивная сумма через 1 общий аккумулятор может оказаться и неправильной, и медленной. Поэтому хороший параллельный алгоритм старается выполнять основную работу независимо, а общий результат объединять как можно реже».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

«Не требуется передачи сообщений» относится к явным операциям уровня MPI. Внутри машины остаются обращения к памяти, передача линий кэша, когерентность и NUMA-трафик. Не обещайте бесплатного взаимодействия.

## Слайд 6. Инкрементальное распараллеливание

🗣 **ГОВОРИМ:**

> «OpenMP позволяет распараллеливать программу постепенно. Сначала находим дорогой цикл и сохраняем правильный последовательный результат. Затем убеждаемся, что итерации независимы, добавляем директиву, проверяем ответ и только после этого измеряем время. Не требуется сразу переписывать всю программу. Но компилятор не докажет за нас, что выбранный цикл можно безопасно разделить. Правильный синтаксис pragma ещё не означает правильный алгоритм: например, общая сумма без редукции остаётся ошибкой».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

Игнорирование pragma при обычной сборке не гарантирует сборку всего исходника: omp.h и вызовы omp_get_wtime/omp_get_thread_num зависят от OpenMP-окружения. Вариант с 1 потоком OpenMP и отдельная последовательная реализация — полезные, но разные базы для измерения накладных расходов.

## Слайд 7. Fork–join

🗣 **ГОВОРИМ:**

> «Модель fork–join удобно представить как разветвление и слияние. До параллельной области работает 1 поток. В parallel появляется команда: основной поток тоже участвует в работе вместе с остальными. В конце все участники должны завершить область, после чего последовательное продолжение выполняет 1 поток. На схеме это несколько линий между точками разветвления и слияния. Важно, что программа может входить в такие области много раз; слишком мелкие области создают лишние накладные расходы».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

Fork здесь — название модели, а не системный вызов fork() для создания процесса. Библиотека может хранить пул системных потоков и переиспользовать его. Не утверждайте, что при каждом parallel ОС обязательно создаёт и уничтожает потоки.

## Слайд 8. Что делает parallel

🗣 **ГОВОРИМ:**

> «Самое важное правило parallel: весь его блок выполняется каждым потоком команды. Если внутри написать обычный цикл от 0 до 99, каждый поток пройдёт все 100 итераций. Работа сама не поделится. Для распределения итераций нужна отдельная директива for либо объединённая запись parallel for. Если забыть это различие, вместо ускорения можно получить повторный подсчёт или несколько потоков, одновременно записывающих одинаковые элементы. В конце parallel есть обязательная синхронизация команды».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

На слайде сокращённое #parallel; в C/C++ нужна запись #pragma omp parallel. Фраза про уничтожение потоков описывает логическое завершение команды, а не обязательное уничтожение системных потоков. Master thread в старой терминологии — основной поток команды.

> [!quote]- 📖 Оригинал на слайде
> ```text
> Обзор  технологии  OpenMP
> Принципы  организации  параллелизма
> • При выполнении обычного кода (вне параллельных
>   областей) программа исполняется одним потоком (master
>   thread)
> • При появлении директивы #parallel происходит создание
>   “команды” (team) потоков для параллельного выполнения
>   вычислений
> • После выхода из области действия директивы #parallel
>   происходит синхронизация, все потоки, кроме master,
>   уничтожаются
> • Продолжается последовательное выполнение кода (до
>   очередного появления директивы #parallel)
> ```

## Слайд 11. Синтаксис

🗣 **ГОВОРИМ:**

> «В C и C++ директива начинается с #pragma omp, затем идёт имя конструкции и её параметры. Например, parallel задаёт параллельную область, а private перечисляет переменные, отдельные для каждого потока. Директива относится к следующему блоку или циклу, поэтому её положение в тексте программы существенно. ## Слайд 12. Лексическая и динамическая область

🗣 **ГОВОРИМ:**

> «Слева, в root.cpp, внутри parallel вызывается TypeThreadNum(). Каждый поток команды выполняет этот вызов. При каждом вызове num своя, поэтому каждый поток сохраняет собственный номер. Перед printf стоит critical: в этот участок одновременно входит только 1 поток. Порядок приветствий при этом не задан. Теперь смысл схемы: лексический контекст — текст внутри фигурных скобок parallel слева. Динамический контекст включает и выполнение вызванной функции справа. ## Слайд 23. Nowait и порог распараллеливания

🗣 **ГОВОРИМ:**

## Слайд 29. Reduction

🗣 **ГОВОРИМ:**

> «Редукция решает задачу общей суммы. Вместо одновременной записи в 1 s потоки накапливают свои частичные значения. После работы OpenMP объединяет их и возвращает результат в исходную переменную. Для индексов от 0 до 99 сумма равна 4950. Начальная общая s тоже учитывается: если начать с 10, получится 4960. Это принципиальное отличие от private: отдельные аккумуляторы нужно не просто создать, но ещё правильно инициализировать и объединить».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

Для reduction(+:s) локальный начальный элемент равен 0. Порядок объединения обычно не фиксирован: для вещественных чисел нужны допустимая погрешность и последовательная база, а не обещание побитового совпадения. Здесь целочисленный результат помещается в int.

**Исправленный пример / фрагмент:**

```c
int s = 0;
```

## Слайд 34. Суммы строк

## Слайд 37. Dynamic и nowait

🗣 **ГОВОРИМ:**

> «Разберём, кто здесь что делает. До parallel работает 1 поток: он создаёт массивы по 1000 элементов и записывает в a[i] и b[i] значение i. Второй цикл должен сложить соответствующие элементы этих массивов и записать ответы в c. Например, c[17] должно получиться равным 17 + 17 = 34.
>
> Директива parallel формирует команду потоков. Массивы a, b и c у них общие — это означает shared. А счётчик i у каждого потока свой — это означает private(i). Следующая директива omp for распределяет между этими потоками 1000 итераций цикла. Каждый индекс обрабатывается 1 раз: потоки не выполняют каждый по полной копии цикла.
>
> Как именно делится работа? В chunk записано 100, поэтому schedule(dynamic, chunk) делит цикл на 10 блоков: индексы 0–99, 100–199 и так далее до 900–999. Допустим, 1 поток получил блок 0–99, а другой — 100–199. Каждый считает свой блок, затем получает ещё 1 свободный блок, если такие остались. Так продолжается, пока все блоки не будут выполнены. Заранее закреплённого набора блоков за каждым потоком здесь нет. Число 100 задаёт размер блока, а не число потоков.
>
> Почему потоки могут считать одновременно? Для c[17] нужны только a[17] и b[17], а для c[18] — только a[18] и b[18]. Входные массивы во время этого цикла не меняются, и каждый элемент c записывает только 1 поток. Поэтому вычисление 1 элемента не требует результата вычисления другого.
>
> Теперь представим: невыданных блоков уже нет, 1 поток закончил свой последний блок, а другой ещё считает. Обычно в конце omp for стоит неявный барьер: закончивший поток ждёт, пока остальные тоже закончат цикл. Слово nowait снимает это ожидание и разрешает потоку перейти к следующей команде внутри parallel. Но здесь следующей стоит закрывающая скобка parallel. На выходе из этой области тоже есть обязательный барьер. Поэтому поток сразу приходит к другому месту ожидания. После parallel вычисление продолжит 1 основной поток, и к этому моменту весь массив c будет готов.
>
> Для чего тогда бывает полезен nowait? Если между концом цикла и концом parallel есть другая работа, не требующая ещё неготовых элементов c, освободившийся поток может заняться ею, пока остальные заканчивают цикл. На этом слайде такой работы нет.
>
> И только теперь обсудим скорость. Здесь каждая итерация делает одинаковую короткую работу: читает 2 элемента, складывает их и записывает ответ. При static можно заранее разделить индексы между потоками. При dynamic во время выполнения нужно ещё согласовывать, какой свободный блок кому достанется. Эта служебная работа тоже занимает время. Dynamic полезен, когда позволяет потокам, которые справляются быстрее, выполнить больше блоков; в этом равномерном цикле причина выбирать его заранее не очевидна. Какой вариант быстрее, проверяем измерением».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

Число потоков в исходнике не задано; 2 потока в устном разборе — иллюстрация, а не свойство программы. При dynamic не фиксируйте соответствие блоков номерам потоков или одинаковое число блоков у всех участников. Поток, закончивший 1 блок, продолжает получать работу, пока остаются невыданные блоки: nowait не позволяет бросить оставшиеся итерации.

Разница между 2 вариантами в этом примере:

- Без nowait: свой последний блок → барьер for → барьер на выходе из parallel.
- С nowait: свой последний блок → сразу барьер на выходе из parallel.

Это схема точек синхронизации по стандарту; реализация может оптимизировать соседние барьеры. Nowait может убрать служебные затраты отдельного барьера, поэтому не обещайте ни нулевого эффекта, ни обязательного ускорения. Конкретный вывод для слайда: между циклом и концом parallel нет другой работы, которую поток мог бы начать раньше остальных. В варианте с такой работой нельзя без дополнительного обоснования читать произвольные элементы c до общей синхронизации; после завершения parallel весь c готов.

Shared не делает запись автоматически безопасной. В этом примере безопасность обеспечена тем, что итерации записывают разные элементы c, не читают результаты друг друга, а a и b уже инициализированы и не изменяются. Предполагается отсутствие наложения массивов, как в объявлениях на слайде. Число блоков равно 1000/100 = 10; это не число потоков. Для измерений нужен достаточно большой объём работы и использование/проверка c после области, иначе оптимизатор может устранить ненужное вычисление.

Семантика директив сверена со спецификацией OpenMP: [распределение цикла](https://www.openmp.org/spec-html/6.0/openmpse88.html), [schedule](https://www.openmp.org/spec-html/6.0/openmpsu140.html), [nowait](https://www.openmp.org/spec-html/5.2/openmpse94.html), [завершение parallel](https://www.openmp.org/spec-html/6.1/openmpse107.html).

## Слайд 38. Sections: синтаксис

🗣 **ГОВОРИМ:**

> «Sections подходит, когда есть несколько разных независимых блоков, а не длинный набор одинаковых итераций. Например, 1 блок считает статистику входной матрицы, другой копирует её в отдельный массив. Внутри sections каждый блок помечен section и выполняется 1 раз. Это не означает «каждый поток выполняет все секции». Если секций всего 2, одновременно выполнять здесь больше 2 полезных работ невозможно, сколько бы потоков мы ни запросили».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

Один поток может выполнить несколько секций; конкретное распределение секций между номерами потоков не задаётся переносимым образом. У sections обычно есть барьер на выходе, снимаемый nowait. Код section должен структурно принадлежать sections.

## Слайд 42. Объединённые конструкции

🗣 **ГОВОРИМ:**

## Слайд 43. Как устроена редукция

🗣 **ГОВОРИМ:**

> «Редукция — это получение 1 результата из нескольких частичных результатов. Для суммы операция объединения — сложение. Что делает reduction(+:total) в нашем parallel for? Внутри цикла каждый поток накапливает свой результат в приватной копии total, которая начинается с 0. Например, 1 поток получил частичную сумму 30, другой — 70. При завершении области OpenMP объединяет эти вклады; если исходная total была 0, снаружи получаем 100. Отдельная строка total += value в теле цикла меняет копию своего потока. Потокам не приходится на каждой итерации изменять 1 общую total».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

[Семантика reduction](https://openmp.org/spec-html/5.2/openmpsu52.html): локальные копии и последующее объединение с исходным значением. [Порядок объединения](https://www.openmp.org/spec-html/5.2/openmpsu50.html) не обещает побитовой повторяемости. Не утверждайте, что реализация обязана использовать 1 конкретное дерево или создавать строго 1 копию на поток во всех видах конструкций.

> ```text

> 
> • Параметр    reduction    определяет   список
>   переменных, для которых выполняется операция
>   редукции
>    – перед выполнением параллельной области для каждого
>      потока создаются копии этих переменных,
>    – потоки формируют значения в своих локальных

>    – при завершении параллельной области на всеми

🗣 **ГОВОРИМ:**

## Слайд 46. Master и single

🗣 **ГОВОРИМ:**

> «Иногда действие нужно выполнить 1 раз за всю команду. Например, потоки считают части задачи, а сообщение о результате должен напечатать кто-то 1. Single поручает блок любому 1 потоку, остальные ждут его завершения. Master поручает блок именно потоку 0; остальные пропускают этот блок и идут дальше. ## Слайд 51. Critical

🗣 **ГОВОРИМ:**

> «Critical означает: этот блок потоки выполняют по очереди. Например, каждый поток посчитал свою сумму и хочет добавить её к общей total. Один входит в critical и выполняет добавление. Другой, если тоже дошёл до critical, ждёт освобождения блока. Затем добавляет свой вклад. Так каждый поток выполняет нужное действие, а изменения общей переменной не мешают друг другу. Внутри critical может быть несколько связанных команд».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

Корректная именованная запись — #pragma omp critical(maximum), со скобками. Все critical с одинаковым именем используют общее взаимное исключение; все безымянные critical также исключают друг друга. Разные имена не защитят обращения к 1 общему объекту друг от друга. У critical нет общего барьера команды: потоки ждут доступ к защищённому блоку по мере обращения. Не помещайте весь дорогой цикл внутрь critical, если требуется параллелизм.

> • Директива critical определяет фрагмент кода, который
>   должен выполняться только одним потоком в каждый
>   текущий момент времени (критическая секция)
>

## Слайд 53. Максимум сумм строк

🗣 **ГОВОРИМ:**

> «Каждый поток считает сумму своей строки. Общая smax хранит наибольшую из уже найденных сумм. Первый if спрашивает: наша сумма вообще больше известного максимума? Если да, поток входит в critical и проверяет ещё раз. Например, мы получили 20 и увидели максимум 10. Но пока ждали, другой поток записал 30. Поэтому после входа 20 уже не нужно записывать. Первый if сокращает число входов в critical, второй не даёт затереть более крупный результат».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

**Для запуска:** замысел 2 проверок объяснён в речи. В буквальном коде отдельно требуется согласовать внешнее чтение smax с её изменениями другими потоками; подробности и варианты ниже.

Сверено по изображению PDF 53, книжная страница 147, и по текстовому пособию, пример 5.9. Автор прямо объясняет обе проверки: уменьшение числа входов в critical и обязательное повторное сравнение после входа. Это намеренная оптимизация с двойной проверкой (double-checked locking), а не случайно продублированный if.

Роль внутренней проверки видна на таком порядке действий; для разбора замысла здесь временно предполагаем, что внешнее чтение возвращает целиком одно из записанных значений:

| Шаг | Поток A: sum=20 | Поток B: sum=30 | smax |
| --- | --- | --- | --- |
| 1 | Внешний if: 20 > 10, проходит | | 10 |
| 2 | Ещё не вошёл в critical | Входит, проверяет и записывает 30 | 30 |
| 3 | Входит в critical | Вышел из critical | 30 |
| 4 | Внутренний if: 20 > 30 ложно, запись пропускается | | 30 |

Если убрать только второй if, на шаге 4 поток A запишет 20 и уменьшит уже найденный максимум. Если убрать внешний if и оставить сравнение под защитой, логика будет корректной, но вход в секцию потребуется для каждой строки.

**Ограничение книжного кода — несинхронизированное внешнее чтение.** Предположение о чтении целого старого значения помогает понять замысел: при только возрастающем smax устаревшее меньшее значение может вызвать лишний вход в секцию, а повторная проверка отсеет ненужную запись. Однако модель памяти OpenMP не гарантирует, что гонка сводится к такому безобидному устареванию. Это не только новое требование: [OpenMP 2.5, §1.4.1, с. 10–11](https://www.openmp.org/wp-content/uploads/spec25.pdf) уже оставляет результат при гонке неопределённым спецификацией; то же правило дано в [OpenMP 5.2, §1.4.1](https://www.openmp.org/spec-html/5.2/openmpsu9.html). Захват critical после чтения не защищает это чтение задним числом.

Ниже простой вариант после вычисления локальной sum: все конкурентные обращения к smax используют одну critical(maximum). Вариант с сохранением 2 проверок и атомарными обращениями дан на [слайде 58](#слайд-58-замок-и-двойная-проверка). Для 1 значения также подходит reduction(max:smax), если поддерживается компилятором. Для верхнетреугольного исходного примера внутренний j начинается с i.

**Исправленный пример / фрагмент:**

```c
// До parallel: double smax = -DBL_MAX;
// Внутри итерации: sum уже вычислена локально.
#pragma omp critical(maximum)
{
    if (sum > smax)
        smax = sum;
}
```

## Слайд 54. Atomic

🗣 **ГОВОРИМ:**

> «Теперь рассмотрим 1 действие: добавить sum к общей total. Поток должен прочитать total, прибавить свой вклад и записать новое значение. Atomic позволяет выполнить это обновление неделимо относительно других атомарных обращений к total: вклады не теряются. Для такого добавления подходят и atomic, и critical. Отличие в том, что critical задаёт очередь для целого блока команд, а atomic описывает определённую операцию над одной переменной».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

Critical ограничивает выполнение блока, atomic update обеспечивает неделимость обновления конкретного объекта в поддерживаемой форме. Atomic может реализовываться аппаратной командой или циклом повторных попыток; более узкое требование даёт реализации возможность снизить накладные расходы, но не гарантирует ускорение. Это не обещание «выполнить любую строку кода за 1 машинную команду».

Если часть потоков обновляет x через atomic, а часть одновременно обращается к x обычным способом, в том числе внутри critical, общей защиты от гонки нет. Не смешивайте эти способы для конкурентных обращений к одному объекту. Поддерживаемые формы read/write/update/capture/compare и порядок памяти различаются; не переносите упрощённый список старого слайда на любые выражения.

## Слайд 55. Сумма через atomic

🗣 **ГОВОРИМ:**

> «На слайде 2 суммы. Sum — сумма текущей строки: поток обнуляет её, проходит элементы строки и складывает их. Total — общая сумма по всем строкам. Закончив строку, поток добавляет sum в total через atomic. Например, для 1000 строк будет 1000 защищённых добавлений в общую total. Если поставить critical вокруг того же добавления, общая total тоже будет обновляться после каждой строки».

> «При reduction(+:total) организация другая. Каждый поток накапливает сумму доставшихся ему строк у себя, а в конце OpenMP объединяет частичные суммы. Например, каждый из 4 потоков может сложить по 250 строк в своём накопителе. Поэтому основное накопление идёт отдельно у каждого потока. Atomic и critical защищают добавления в общую total; reduction организует частичные суммы и их объединение».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

Книжная страница 146. Код суммирует j от i до NMAX−1, то есть верхнюю треугольную часть. Для суммы всей прямоугольной матрицы начните j с 0. Не выдавайте исходный треугольный вариант за общий случай. В примерах ниже сохранён исходный диапазон j, исправлена лишняя { перед for, sum объявлена внутри итерации, total имеет тип double; печать убрана.

**Исправленные примеры / фрагменты для сравнения:**

В каждом варианте предполагаются одна и та же подготовленная матрица a размера NMAX × NMAX и отдельная инициализация total = 0. Итог читаем после завершения parallel for.

**1. Atomic: общая total обновляется после каждой строки.**

```c
double total = 0.0;
#pragma omp parallel for default(none) shared(a, total)
for (int i = 0; i < NMAX; ++i) {
    double sum = 0.0;
    for (int j = i; j < NMAX; ++j)
        sum += a[i][j];
    #pragma omp atomic update
    total += sum;
}
```

**2. Critical: в том же цикле заменить atomic и следующую строку этим блоком.** Число обновлений общей total не изменится.

```c
#pragma omp critical(total_update)
{
    total += sum;
}
```

**3. Reduction: внутри цикла total обозначает приватный накопитель потока.** Она сохраняет накопленный вклад между его итерациями; обнуляется перед каждой строкой только sum.

```c
double total = 0.0;
#pragma omp parallel for default(none) shared(a) reduction(+:total)
for (int i = 0; i < NMAX; ++i) {
    double sum = 0.0;
    for (int j = i; j < NMAX; ++j)
        sum += a[i][j];
    total += sum;  // Здесь total приватная: atomic не требуется.
}
// Здесь исходная total содержит объединённый результат.
```

| Вопрос | Critical вокруг добавления | Atomic на добавлении | Reduction для цикла |
| --- | --- | --- | --- |
| Куда добавляется сумма строки? | В общую total | В общую total | В приватную копию total |
| Что происходит после каждой строки? | Вход в защищённый блок и обновление общей total | Атомарное обновление общей total | Прибавление к приватной total |
| Как получается итог? | Уже накоплен в общей total | Уже накоплен в общей total | OpenMP объединяет частичные результаты |

Ручное накопление за несколько строк тоже возможно: поток может собрать свой вклад, а затем 1 раз добавить его через atomic или critical. Значит, частота обращений к общей сумме определяется размещением накопления и объединения в алгоритме. Critical и atomic сами по себе её не задают. Reduction поручает приватное накопление и объединение OpenMP.

Для этого обычного parallel for без simd удобно объяснять редукцию через 1 накопитель на поток. Стандарт допускает дополнительные копии и не задаёт точное число, порядок и способ операций объединения. Не обещайте «ровно 4 атомарных обновления» или обязательное дерево. Начальное значение исходной total также участвует в результате. Скорость вариантов проверяют измерением; при double возможны небольшие различия из-за порядка сложения.

Семантика сверена по спецификации: [critical](https://www.openmp.org/spec-html/5.2/openmpse90.html), [atomic](https://www.openmp.org/spec-html/5.2/openmpsu125.html), [reduction](https://www.openmp.org/spec-html/5.2/openmpsu52.html).

## Слайд 58. Замок и двойная проверка

🗣 **ГОВОРИМ:**

> «Здесь тот же максимум, что на слайде 53, но очередь задаётся явным замком. Читаем 4 действия: если наша сумма больше максимума — взять замок; после захвата сравнить ещё раз; при необходимости записать новую smax; освободить замок. Вторая проверка нужна потому, что другой поток мог повысить максимум, пока мы ждали. Первый if позволяет не брать замок для заведомо меньшей суммы. Оба if поставлены намеренно».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

**Для запуска:** 2 if сохраняют смысл, но внешнее чтение обычной smax требует отдельного согласования с записью. Простой вариант с замком до сравнения и вариант с 2 проверками показаны ниже.

Сверено по изображению PDF 58 и примеру 5.10 на книжных страницах 148–149. В книге он прямо назван переработкой примера 5.9 с critical, где назначение 2 if объяснено словами. Замок обеспечивает взаимное исключение между потоками, которые его захватывают, и синхронизацию при передаче замка; эти гарантии не распространяются на внешнее чтение до захвата. [Функции замков OpenMP, §18.9](https://www.openmp.org/spec-html/5.2/openmpse114.html).

Дополнительно перед for в исходнике лишний блок. Ниже фрагменты внутри итерации; sum локальная, smax и lock общие, lock инициализирован до области и уничтожается после неё. Предполагаются конечные суммы строк; smax инициализирована значением -DBL_MAX. При NaN/бесконечностях и пустом входе политику результата задают отдельно.

**Исправленный пример / фрагмент:**

```c
omp_set_lock(&lock);
if (sum > smax)
    smax = sum;
omp_unset_lock(&lock);
```

**Вариант с сохранением 2 проверок:**

```c
// Внутри итерации после вычисления локальной sum.
double observed;  // локальная переменная этой итерации
#pragma omp atomic read
observed = smax;

if (sum > observed) {
    omp_set_lock(&lock);

    #pragma omp atomic read
    observed = smax;
    if (sum > observed) {
        #pragma omp atomic write
        smax = sum;
    }

    omp_unset_lock(&lock);
}
```

Все обращения к smax, которые могут выполняться одновременно, здесь атомарные. Под замком атомарные read и write тоже нужны: внешний читатель замок не захватывает, поэтому обычная запись внутри замка с ним не согласована. Сам замок объединяет внутреннее сравнение и возможную запись в 1 защищённое действие относительно других обновляющих потоков. Безопасное чтение старого меньшего максимума может привести к лишнему захвату; внутренняя проверка предотвратит уменьшение smax. Здесь максимум только возрастает, поэтому пропуск обновления при sum ≤ observed безопасен. Это рассуждение относится к показанному протоколу, а не к произвольному коду с 2 if.

Формы atomic read/write и требование согласовать все потенциально конкурентные обращения описаны в [OpenMP 5.1, §2.19.7](https://www.openmp.org/spec-html/5.1/openmpsu105.html). Только добавить atomic read снаружи, сохранив обычную запись под замком, недостаточно. Пример показывает, как сохранить замысел учебника; ускорение по сравнению с простой блокировкой требует измерения.

## Слайд 59. Barrier

🗣 **ГОВОРИМ:**

> «Барьер — место, где потоки ждут друг друга. Например, каждый заполняет свою часть массива, а следующий этап должен использовать весь заполненный массив. Быстрый поток доходит до barrier и ждёт. Когда последний поток тоже дошёл, все могут продолжить. Поэтому после барьера можно начинать следующий этап: никто больше не занят заполнением своей части. Это ожидание всей команды, а не очередь на выполнение одного блока».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

В обычном omp for уже есть неявный барьер на выходе, если не задан nowait. Все потоки соответствующей команды должны согласованно встретить явный barrier. Барьер только в ветви 1 потока или внутри распределённого цикла — неверная структура для нашего примера.

## Слайд 60. Flush

🗣 **ГОВОРИМ:**

> «Общая переменная доступна всем потокам, но это ещё не значит, что каждый поток немедленно увидит её новое значение. Компилятор и процессор могут временно сохранять значения и менять порядок обращений к памяти. Flush относится к согласованию этих обращений с общей памятью. Он не собирает потоки в одной точке, как barrier. В обычных примерах нужное согласование уже входит в работу barrier, critical и других средств синхронизации; отдельный flush нужен для более специальных схем обмена».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

Слайд упрощает модель памяти. Существуют корректные протоколы с flush при соблюдении всех требований стандарта, поэтому утверждение «flush никогда не нужен» тоже неверно. Но одиночный flush у пишущего потока не доказывает корректность чтения в цикле другого; см. слайд 65.

## Слайд 62. Повтор critical

🗣 **ГОВОРИМ:**

## Слайд 63. Барьер между этапами

🗣 **ГОВОРИМ:**

> «Здесь вводится барьер: дошедший до него поток ждёт остальных участников команды. Представим 2 этапа: сначала потоки заполняют массив, затем используют готовые данные. Барьер ставим между этими этапами. В случае omp for ожидание обычно уже есть в конце всего распределённого цикла: второй этап начнётся после завершения всех его итераций. На этом примере важно различать конец одной итерации и конец работы всей команды над циклом».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

**Для запуска:** на изображении PDF 63 barrier действительно расположен внутри тела omp for. Так вкладывать barrier нельзя; его место — между этапами, после завершения распределённого цикла. Это конкретная ошибка расположения директивы. Ограничение — [OpenMP, правила вложения](https://www.openmp.org/spec-html/5.1/openmpse30.html). Ниже исправленный пример: после первого for все элементы готовы, затем 1 поток печатает их сумму. При n ≥ 0 результат n · (n − 1)/2.

**Исправленный пример / фрагмент:**

```c
void barrier_example(int n, int *a) {
    #pragma omp parallel default(none) shared(n,a)
    {
        #pragma omp for
        for (int i = 0; i < n; ++i)
            a[i] = i;
        // Неявный барьер завершившегося omp for.
        #pragma omp single
        {
            long long sum = 0;
            for (int i = 0; i < n; ++i)
                sum += a[i];
            printf("Sum: %lld\n", sum);
        }
    }
}
```

## Слайд 64. Гистограмма

🗣 **ГОВОРИМ:**

> «Здесь результаты складываются в ячейки массива x. Индекс нужной ячейки берётся из index[i]. Например, у 2 разных итераций index[i] равен 3: обе хотят увеличить x[3]. Если они одновременно прочитают старое значение и запишут новое, 1 вклад может потеряться. Atomic защищает каждое добавление в выбранную ячейку. Поэтому обе итерации добавят свой вклад, даже когда попали в одну ячейку».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

Перед накоплением x нужно инициализировать. Функция count(i) в исходнике тоже должна быть безопасна для параллельного вызова: atomic защищает обновление выбранной ячейки, а не произвольные действия внутри count. Проверьте 0 ≤ index[i] < M.

## Слайд 65. Передача сигнала через общий флаг

🗣 **ГОВОРИМ:**

> «Посмотрим, какой обмен задумал автор. В начале общий x равен 0. Первая секция записывает x=1: это сигнал «готово». Вторая выполняет while (!x): пока видит 0, остаётся в цикле, а увидев 1 — выходит. Flush после записи должен иллюстрировать согласование значения с общей памятью. Это пример идеи передачи сигнала между потоками; для рабочей программы показанный обмен нужно дополнить, как разобрано в примечании».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

**Для запуска:** это неполный пример обмена через флаг. Flush у записывающего потока не обеспечивает, что другой поток будет заново читать x в while (!x); обычные чтение и запись здесь не образуют согласованного обмена. Это подтверждается [описанием flush в OpenMP, §2.19.8](https://www.openmp.org/spec-html/5.1/openmpsu106.html). Есть и отдельное условие выполнения: sections не гарантирует 2 потока. Если единственный поток сначала возьмёт ожидающую секцию, он не дойдёт до записи x=1.

Для вводного рабочего примера ниже выбран single с барьером: 1 поток готовит значение, остальные продолжают после завершения подготовки. Это показывает готовность данных между этапами. Саму идею флага готовности со слайда не объявляем бессмысленной; для её реализации нужен полный протокол обмена.

**Исправленный пример / фрагмент:**

```c
int x = 0;
#pragma omp parallel default(none) shared(x)
{
    #pragma omp single
    {
        x = 1;
    }
    // Барьер single завершён: дальше все могут читать x.
    // Новых записей в x здесь нет.
}
```

## Слайд 66. Порядок вывода через ordered

🗣 **ГОВОРИМ:**

> «В каждой итерации сначала выполняется работа: k задаёт число повторов, цикл несколько раз вычисляет sin. Поэтому разные итерации могут закончить эту работу в разное время. Затем идут 2 печати. Первая, No order, печатает номер i без требования порядка: например, 2, 0, 3, 1. Перед второй стоит omp ordered, поэтому строки Order идут по номерам итераций: 0, 1, 2, 3. Если итерация 2 дошла сюда раньше итерации 0, она подождёт своей очереди. Работа до ordered при этом может выполняться параллельно».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

**Как читать код:** i — номер внешней итерации; k — число повторов внутреннего цикла; j — его счётчик; x — промежуточное значение для sin. Эти вычисления нужны, чтобы перед печатью была работа разной длительности. Итоговый x на исходном слайде не печатается: сравниваются только порядки вывода i.

У ordered здесь 2 места записи: параметр ordered в строке parallel for разрешает упорядоченный участок в этом цикле; отдельная директива omp ordered отмечает сам участок. Гарантия относится к последовательности строк Order. Строки No order могут появляться между ними. No order тоже может случайно выйти по возрастанию; обязательного перемешивания нет. [Описание ordered в OpenMP, §2.19.9](https://www.openmp.org/spec-html/5.1/openmpsu107.html).

**Для запуска исходного примера:** переменные j, k и x объявлены перед parallel for. В этой C-программе i — индекс распределяемого цикла и автоматически приватен, а j, k и x без private остаются общими. Например, один поток может менять k, пока другой проверяет j < k. Поэтому для них нужно добавить private(j,k,x) либо перенести объявления внутрь итерации. Это поправка к временным переменным примера; работа самой ordered на слайде показана по назначению. [Правила атрибутов данных OpenMP, §5.1.1](https://www.openmp.org/spec-html/5.2/openmpsu33.html).

**Минимальный пример для сравнения двух печатей:**

Здесь оставлены только действия, которые демонстрируют ordered; генератор случайных чисел и вычисление sin для этого не нужны. Предполагается #include <stdio.h>.

```c
void ordered_example(void) {
    #pragma omp parallel for ordered
    for (int i = 0; i < 4; ++i) {
        printf("No order: %d\n", i);
        #pragma omp ordered
        {
            printf("Order: %d\n", i);
        }
    }
}
```

При команде из 4 потоков, если выделить только строки каждого вида, возможен такой результат:

| Вид строк | Номера i в порядке появления |
| --- | --- |
| No order | 2, 0, 3, 1 |
| Order | 0, 1, 2, 3 |

Таблица показывает 2 последовательности внутри одного вывода, а не 2 последовательных запуска. Каждый номер печатается 2 раза. Для измерения скорости печать убирают; этот пример предназначен для наблюдения порядка.

>   master

### Вопрос 1. Какие компьютерные платформы относятся к числу вычислительных систем с общей памятью?

**Ответ:** К системам с общей памятью относятся многоядерные компьютеры, многопроцессорные SMP-системы и ccNUMA-системы: их процессоры могут обращаться к общей памяти в едином адресном пространстве. В ccNUMA время доступа зависит от расположения данных. Обычный кластер имеет распределённую память между узлами; OpenMP обычно используют внутри узла, а MPI — для связи между узлами.

### Вопрос 2. Какие подходы используются для разработки параллельных программ?

**Ответ:** Используют автоматическое распараллеливание компилятором, директивы высокого уровня, явное создание потоков и обмен сообщениями между процессами. Примеры: OpenMP, POSIX Threads или потоки C++, MPI. Возможны гибридные программы MPI + OpenMP. Выбор зависит от архитектуры памяти, структуры задачи и требуемого контроля над исполнением.

### Вопрос 3. В чем состоят основы технологии OpenMP?

**Ответ:** OpenMP — стандартный интерфейс параллельного программирования на C, C++ и Fortran. Он включает 3 части: директивы компилятора, функции библиотеки времени исполнения и переменные окружения. В рассматриваемой CPU-модели используется общая память и схема fork–join: поток формирует команду для параллельной области, затем участники синхронизируются, и выполнение продолжается исходным потоком.

### Вопрос 4. В чем состоит важность стандартизации средств разработки параллельных программ?

**Ответ:** Стандарт задаёт единый синтаксис и смысл директив, функций и правил работы с памятью. Это позволяет переносить исходный код между совместимыми компиляторами и платформами, пользоваться общей документацией и повторно использовать библиотеки. Переносимость требует поддержки использованных возможностей; одинаковая производительность и одинаковое расписание исполнения стандартом не гарантируются.

### Вопрос 5. В чем состоят основные преимущества технологии OpenMP?

**Ответ:** OpenMP позволяет постепенно распараллеливать существующую программу, начиная с дорогих независимых циклов. Директивы сокращают объём служебного кода, а общая память упрощает доступ к общим массивам. Единый стандарт облегчает перенос между платформами и сохранение последовательного варианта. Корректность зависимостей и фактическое ускорение всё равно нужно проверять.

### Вопрос 6. Что понимается под параллельной программой в рамках технологии OpenMP?

**Ответ:** В рамках этой лекции это программа на C, C++ или Fortran, где последовательные участки чередуются с параллельными областями OpenMP. Внутри области команда потоков выполняет код и распределяет работу с помощью `for`, `sections` и других конструкций. Общие данные и синхронизация задаются явно или по правилам OpenMP; наличие директив само по себе не доказывает ускорения.

### Вопрос 7. Что понимается под понятием потока (thread)?

**Ответ:** Поток — отдельный поток исполнения команд внутри процесса, со своим состоянием исполнения, стеком и приватными данными. Потоки процесса имеют доступ к общим объектам в его адресном пространстве. Номер из `omp_get_thread_num()` обозначает участника текущей команды; он не является номером физического ядра.

### Вопрос 8. Какие возникают проблемы при использовании общих данных в параллельно выполняемых потоках?

**Ответ:** Главная проблема — гонка данных: потоки обращаются к одной области памяти, хотя бы 1 доступ является записью, а нужного упорядочивания нет. Например, одновременные `sum += x` могут терять обновления. Также нужно учитывать зависимости между этапами, видимость изменений и взаимные блокировки при неверной синхронизации. Конкуренция за память и ложное разделение кэш-линии могут снижать скорость даже корректной программы.

### Вопрос 9. Какой формат записи директив OpenMP?

**Ответ:** В C/C++ используется форма `#pragma omp` с именем конструкции и допустимыми параметрами, например `#pragma omp parallel private(x)`. Для блочной конструкции далее идёт структурированный блок, а за `#pragma omp parallel for` непосредственно следует цикл `for`. Во Fortran свободной формы директива начинается с `!$omp`, например `!$omp parallel`, и при необходимости имеет завершающую директиву `!$omp end parallel`.

### Вопрос 10. В чем состоит назначение директивы parallel?

**Ответ:** `parallel` формирует команду потоков, каждый из которых выполняет связанный с директивой блок. Поток, встретивший конструкцию, становится основным в новой команде и получает номер 0. В конце области есть обязательный неявный барьер; затем внешний код продолжает исходный поток. Сам по себе `parallel` не распределяет итерации обычного цикла: для этого нужен `for` или объединённая конструкция `parallel for`.

### Вопрос 11. В чем состоит понятие фрагмента, области и секции параллельной программы?

**Ответ:** В терминологии слайда 12 параллельный фрагмент — лексически записанный блок, связанный с директивой `parallel`. Параллельная область — динамическое исполнение этого блока, включая вызванные из него функции. Секция — отдельный структурированный блок под `section` внутри `sections`, который выполняется 1 участником команды. Поэтому директива в вызванной функции может входить в параллельную область, хотя текст функции расположен вне фрагмента.

### Вопрос 12. Какой минимальный набор директив OpenMP позволяет начать разработку параллельных программ?

**Ответ:** Чтобы создать команду, достаточно `parallel`; для первого полезного распределённого цикла удобен `parallel for`, то есть сочетание `parallel` и `for`. В сумме добавляют параметр `reduction(+:sum)`, предварительно задав исходное значение `sum = 0`. Общие входы и приватные временные данные также должны быть определены корректно. Набора директив, который автоматически делает любой алгоритм параллельным и правильным, нет.

### Вопрос 13. Как определить время выполнения OpenMP программы?

**Ответ:** Измеряют прошедшее время: `double t0 = omp_get_wtime();`, затем выполняют нужный участок и вычисляют `double elapsed = omp_get_wtime() - t0;`. Оба вызова выполняет тот же измеряющий поток; к моменту второго вызова вся измеряемая работа должна завершиться. Удобно поставить замеры снаружи `parallel`. Для сравнения фиксируют вход, число потоков и границы замера, убирают лишний вывод и повторяют измерения.

### Вопрос 14. Как осуществляется распараллеливание циклов в OpenMP? Какие условия должны выполняться, чтобы циклы могли быть распараллелены?

**Ответ:** `omp for` распределяет итерации между потоками уже существующей команды, а `parallel for` также формирует команду. Цикл должен иметь допустимую для OpenMP каноническую форму, позволяющую определить пространство итераций. Для обычного распределения без дополнительного упорядочивания итерации должны быть независимы; общую сумму оформляют редукцией. Зависимость вида `a[i] = a[i-1] + 1` нельзя устранить простым добавлением `parallel for`.

### Вопрос 15. Какие возможности имеются в OpenMP для управления распределением итераций циклов между потоками?

**Ответ:** Распределение задаётся параметром `schedule`: `static` заранее назначает части работы; `dynamic` выдаёт очередную порцию освободившемуся потоку; `guided` выдаёт порции с уменьшающимся размером; `auto` передаёт выбор реализации. Для `static`, `dynamic` и `guided` можно указать размер порции. При `schedule(runtime)` настройки берутся из `OMP_SCHEDULE` или `omp_set_schedule()`. Эти настройки меняют распределение работы, сохраняя требования корректности. См. [правила schedule](https://www.openmp.org/spec-html/5.2/openmpsu107.html).

### Вопрос 16. Как определяется порядок выполнения итераций в распараллеливаемых циклах в OpenMP?

**Ответ:** Общий порядок начала и завершения итераций разных потоков обычно не определён: итерация с большим индексом может закончиться раньше. Даже `schedule(static)` задаёт распределение работы, а не общий хронологический порядок. Если выбранный участок должен выполняться в порядке исходного последовательного цикла, используют `ordered` у цикла и `#pragma omp ordered` перед этим участком. Остальная часть тела может исполняться параллельно.

### Вопрос 17. Какие правила синхронизации вычислений в распараллеливаемых циклах в OpenMP?

**Ответ:** В конце `omp for` по умолчанию есть неявный барьер: участники команды дожидаются завершения распределённого цикла. Параметр `nowait` у `for` убирает это ожидание; читать общий итог сразу после такого цикла можно только при наличии нужного упорядочивания. Между соседними итерациями автоматических барьеров нет. Явный `barrier` нельзя помещать внутрь тела распределённого `for`; обязательный барьер конца `parallel` сохраняется.

### Вопрос 18. Как можно ограничить распараллеливание фрагментов программного кода с невысокой вычислительной сложностью?

**Ответ:** Используют параметр `if` у `parallel`, например `#pragma omp parallel for if(n > threshold)`. Если условие ложно, область выполняется командой из 1 потока, и итерации не распределяются между несколькими участниками. Порог выбирают по измерениям стоимости полезной работы и накладных расходов. Чтобы полностью обойти саму конструкцию OpenMP, можно явно выбрать последовательную ветвь обычным `if` в программе.

### Вопрос 19. Как определяются общие и локальные переменные потоков?

**Ответ:** `shared(x)` означает доступ к исходному общему объекту, а `private(x)` — отдельный экземпляр для каждого участника; скалярный приватный экземпляр автоматически исходным значением не инициализируется. `firstprivate(x)` копирует начальное значение, `lastprivate(x)` возвращает значение из логически последней итерации или секции. Применимость параметров зависит от конструкции. `default(none)` требует явно определить атрибуты переменных без предопределённого атрибута; например, индекс `omp for` уже приватен.

### Вопрос 20. Что понимается под операцией редукции?

**Ответ:** Редукция объединяет частичные результаты заданной операцией, например сложением или поиском максимума. При `reduction(+:sum)` создаются приватные аккумуляторы, инициализированные 0, а затем их значения объединяются с исходным `sum`. Для обычной суммы исходный `sum` заранее задают равным 0. Порядок сложения вещественных чисел может отличаться от последовательного, поэтому небольшое расхождение проверяют с допуском.

### Вопрос 21. Какие способы организации взаимоисключения могут быть использованы в OpenMP?

**Ответ:** Используют `critical` для защищённого блока, `atomic` для поддерживаемого атомарного обращения к объекту и библиотечные замки для явного захвата и освобождения. Все конфликтующие обращения должны соблюдать согласованный механизм защиты: `atomic` и обычный доступ из другого потока не образуют безопасную пару. Редукция часто позволяет обойти общий аккумулятор в теле цикла. `barrier` организует ожидание этапа, но не исправляет уже произошедшую гонку.

### Вопрос 22. Что понимается под атомарной (неделимой) операцией?

**Ответ:** Атомарная операция обращается к выбранному объекту как неделимое действие относительно согласованных атомарных обращений к нему. Например, `#pragma omp atomic update` перед `counter += 1;` предотвращает потерю таких обновлений. Защищается только указанное обращение, а не произвольный окружающий блок. Обычная инструкция `counter++` сама по себе атомарность не гарантирует; атомарность счётчика также не означает готовность всех остальных данных.

### Вопрос 23. Как определяется критическая секция?

**Ответ:** Критическая секция задаётся `#pragma omp critical` и следующим блоком; одновременно его может выполнять только 1 участник соответствующей группы конкурирующих потоков. Можно задать имя, например `#pragma omp critical(update_max)`: участки с одинаковым именем используют общее взаимное исключение. Все безымянные `critical` также связаны между собой. Порядок входа потоков не фиксирован; проверку условия и зависимое обновление общего объекта обычно защищают вместе.

### Вопрос 24. Какие операции имеются в OpenMP для переменных семафорного типа (замков)?

**Ответ:** Для простого замка типа `omp_lock_t` предусмотрены `omp_init_lock(&lock)` — инициализация, `omp_set_lock(&lock)` — ожидание и захват, `omp_unset_lock(&lock)` — освобождение, `omp_test_lock(&lock)` — попытка захвата без ожидания и `omp_destroy_lock(&lock)` — уничтожение. Успешный `test_lock` действительно захватывает замок. Освобождает его владеющая задача; уничтожают замок после завершения использования в незахваченном состоянии. Для повторного захвата той же задачей есть `omp_nest_lock_t` и соответствующие функции. См. [операции с замками](https://www.openmp.org/spec-html/5.2/openmpse114.html).

### Вопрос 25. Как осуществляется в OpenMP распараллеливание по задачам (директива sections)?

**Ответ:** Внутри `sections` размещают блоки `section`; каждый блок выполняется ровно 1 раз одним из потоков команды. Сам `sections` новую команду не создаёт; для этого используют внешний `parallel` или `parallel sections`. Назначение блоков потокам не фиксировано: 1 поток может выполнить несколько секций. В конце по умолчанию есть барьер, убираемый `nowait` у `sections`. Зависимые секции требуют синхронизации; это механизм распределения блоков, отличный от конструкции `task`.

### Вопрос 26. Как определяются однопотоковые участки параллельных фрагментов (директивы single и master)?

**Ответ:** Блок `single` выполняет 1 выбранный поток команды, причём не обязательно основной; остальные пропускают блок и по умолчанию ждут на барьере в его конце. `single nowait` убирает этот барьер. Блок `master` выполняет только основной поток текущей команды, с номером 0, и не имеет неявного барьера ни на входе, ни на выходе. Если другие потоки используют полученный результат, ожидание нужно организовать отдельно.

### Вопрос 27. Как осуществляется синхронизация состояния памяти (директива flush)?

**Ответ:** `flush` согласует временное представление памяти вызывающего потока с моделью общей памяти и задаёт ограничения на порядок обращений. Он не является барьером и не делает `x += 1` атомарным. Для передачи данных нужен согласованный протокол на стороне записи и чтения; одиночного `flush` после записи недостаточно. Барьеры, критические секции и другие средства синхронизации уже включают предусмотренное стандартом согласование памяти. См. [описание flush](https://www.openmp.org/spec-html/5.1/openmpsu106.html).

### Вопрос 28. Как используются постоянные локальные переменные потоков (директивы threadprivate и copyin)?

**Ответ:** `threadprivate` создаёт отдельную копию подходящей глобальной или статической переменной для каждого потока. Здесь «постоянная» означает длительно существующую, а не неизменяемую. Параметр `copyin(x)` у `parallel` копирует значение из экземпляра основного потока в экземпляры остальных участников перед выполнением блока; самостоятельной директивы `copyin` нет. Сохранение значений рабочих потоков между областями гарантируется только при выполнении [условий threadprivate](https://www.openmp.org/spec-html/5.2/openmpse24.html); перенос значений задаётся [правилами copyin](https://www.openmp.org/spec-html/5.2/openmpsu58.html).

### Вопрос 29. Какие средства имеются в OpenMP для управления количеством создаваемых потоков?

**Ответ:** Желаемое число потоков задают параметром `num_threads(n)` у конкретного `parallel`, функцией `omp_set_num_threads(n)` для последующих областей в соответствующем контексте и переменной окружения `OMP_NUM_THREADS`. На результат также влияют `if`, динамическая регулировка, ограничения вложенности и `OMP_THREAD_LIMIT`. Фактический размер текущей команды узнают через `omp_get_num_threads()` внутри области; вне параллельной области функция возвращает 1. См. [правила выбора размера команды](https://www.openmp.org/spec-html/5.2/openmpsu95.html).

### Вопрос 30. Что понимается под динамическим режимом создания потоков?

**Ответ:** Динамический режим разрешает библиотеке OpenMP выбирать для новой параллельной области меньше потоков, чем запрошено, с учётом ресурсов. Его включают через `OMP_DYNAMIC=true` или `omp_set_dynamic(1)`, выключают через `false` или `omp_set_dynamic(0)`. Размер уже сформированной команды внутри области остаётся постоянным. Это отдельная настройка от `schedule(dynamic)`, которое распределяет порции итераций внутри команды.

### Вопрос 31. Как осуществляется управление вложенностью параллельных фрагментов?

**Ответ:** Вложенный `parallel` встречается при исполнении уже существующей параллельной области и может сформировать новую команду. Число активных уровней ограничивают `OMP_MAX_ACTIVE_LEVELS` или `omp_set_max_active_levels()`; значения `OMP_NUM_THREADS` можно задать списком по уровням. При исчерпании разрешённых активных уровней новая область выполняется 1 потоком. Указанные на старых слайдах `OMP_NESTED` и `omp_set_nested()` устарели. Вложенность следует ограничивать, чтобы избежать избыточного числа потоков.

### Вопрос 32. В чем состоят особенности разработки параллельных программ с использованием OpenMP на алгоритмическом языке Fortran?

**Ответ:** Основная модель OpenMP сохраняется, меняется языковая запись. В Fortran свободной формы используются `!$omp parallel`, `!$omp do` и соответствующие завершающие директивы; аналог `parallel for` — `!$omp parallel do` перед циклом `do`. Библиотечные функции и типы обычно подключают через `use omp_lib`. Нужно учитывать правила атрибутов данных Fortran, в том числе для `SAVE` и `COMMON`; директивы здесь регистронезависимы. См. [языковые формы директив](https://www.openmp.org/spec-html/5.2/openmpse14.html).

### Вопрос 33. Как обеспечивается единственность программного кода для последовательного и параллельного вариантов программы?

**Ответ:** Общий алгоритм сохраняют в одном исходнике и добавляют директивы OpenMP: при сборке без поддержки OpenMP они обычно игнорируются, а Fortran-директивы воспринимаются как комментарии. В C/C++ подключение `omp.h` и вызовы API при необходимости защищают `#ifdef _OPENMP` и дают последовательную замену, например номер потока 0. Во Fortran есть строки условной компиляции `!$`. Последовательную корректность нужно сохранять по смыслу алгоритма: игнорирования директив для этого недостаточно. См. [условную компиляцию OpenMP](https://www.openmp.org/spec-html/5.2/openmpse16.html).

### Вопрос 34. Какие компиляторы обеспечивают поддержку технологии OpenMP?

**Ответ:** Примеры компиляторов с поддержкой OpenMP: GNU GCC для C/C++ и GNU Fortran, LLVM Clang, Intel oneAPI, NVIDIA HPC SDK и Microsoft Visual C++. Поддерживаемые версии стандарта и возможности различаются; поддержка CPU не означает полной поддержки ускорителей. Поэтому проверяют документацию конкретной версии, параметры сборки и наличие runtime-библиотеки. На macOS команда `gcc` может вызывать Apple Clang и сама по себе ничего не доказывает. См. [официальный перечень компиляторов](https://www.openmp.org/resources/openmp-compilers-tools/).

## Слайд 75. Базовые упражнения

🗣 **ГОВОРИМ:**

> «Для первых работ выберем минимум и максимум вектора, скалярное произведение или интеграл методом прямоугольников. Во всех случаях сначала нужна последовательная база. В интеграле считаем значения функции независимо, суммируем и умножаем на ширину шага. Важная поправка: на произвольном отрезке точка равна a + i * h, а на слайде пропущено a. В задаче по матрице сначала находим минимум каждой строки, затем максимум из полученных значений. Эти 2 уровня нельзя случайно поменять местами».

🧠 **ЗНАТЬ, НО НЕ ГОВОРИТЬ:**

Формулы сверены по изображению PDF 75. На слайде x_i = i · h, что подходит для левого конца a = 0; для общего [a,b] нужно x_i = a + i · h. При N > 0: h = (b − a)/N, I_N = h · Σ(i = 0…N − 1) f(a + i · h). Это левые прямоугольники. Для max_i min_j a[i,j] пример строк [3,1], [5,2]: минимумы 1 и 2, ответ 2. Пустые массивы и строки требуют отдельного условия; проверяйте и отрицательные входы.

## Полная программа для первого запуска

Это самостоятельный пример C: сумма и скалярное произведение для тех же данных, что на слайдах. **Сборка GCC в Linux**:

```sh
gcc -O2 -std=c11 -Wall -Wextra -fopenmp example.c -o example
OMP_NUM_THREADS=2 OMP_DYNAMIC=false ./example
```

Для macOS используйте команды своего окружения из практикума. Время ниже включает вход и выход из parallel, single и распределение цикла. При 100 элементах это проверка устройства программы, а не убедительный опыт ускорения.

```c
#include <stdio.h>
#include <omp.h>

int main(void) {
    enum { N = 100 };
    double a[N], b[N];
    for (int i = 0; i < N; ++i) {
        a[i] = i;
        b[i] = 2.0 * i;
    }
    double sum = 0.0, dot = 0.0;
    int actual = 1;
    double t0 = omp_get_wtime();
    #pragma omp parallel default(none) shared(a,b,actual) reduction(+:sum,dot)
    {
        #pragma omp single
        {
            actual = omp_get_num_threads();
        }
        #pragma omp for schedule(static)
        for (int i = 0; i < N; ++i) {
            sum += a[i];
            dot += a[i] * b[i];
        }
    }
    double elapsed = omp_get_wtime() - t0;
    printf("Threads: %d; sum: %.0f; dot: %.0f; time: %.9f s\n",
           actual, sum, dot, elapsed);
    return (sum == 4950.0 && dot == 656700.0) ? 0 : 1;
}
```

Ожидаются sum = 4950 и dot = 656700 при любом допустимом числе потоков. Именно эти входы дают точно представимые небольшие целые вклады в double; для произвольных вещественных данных используйте допуск. Наличие 1 правильного ответа не является общей проверкой отсутствия гонок в другом коде.

## Вопросы для короткой проверки

| Вопрос | Ожидаемый ответ |
| --- | --- |
| Что будет с обычным for внутри parallel без omp for? | Каждый поток выполнит весь цикл. |
| private(sum) заменяет reduction(+:sum)? | Нет: нет нужного общего объединения; скаляр ещё надо инициализировать. |
| lastprivate(j) возвращает значение самого медленного потока? | Нет: результат логически последней итерации. |
| Почему default(none) не доказывает правильность? | Явные атрибуты не устраняют зависимости и конфликты внутри общих данных. |
| Барьер после гонки исправляет сумму? | Нет: нужно защитить само накопление или использовать редукцию. |
| Чем single отличается от critical? | 1 выполнение выбранным потоком против нескольких обращений по очереди. |
| Можно защитить только запись smax, оставив сравнение снаружи? | Нет: незащищённое конкурентное чтение тоже создаёт гонку. |
| OMP_SCHEDULE меняет schedule(static) в исходнике? | Нет: настройка используется для schedule(runtime). |
| Почему 2 секции не гарантируют 2 разных потока? | Распределение секций не фиксировано; 1 поток может выполнить обе. |
| Почему запуск с 8 потоками не доказывает ускорение в 8 раз? | Нужны корректная база и время; есть накладные расходы, дисбаланс и предел памяти. |
